# Staged remediation ownership

Own bounded implementation through independent acceptance; complement TDD and code review rather than replace them. No automatic deployment authorization.

## User expectations

Amar clarified the MVP delivery preference: reuse and enhance existing ingestion, storage, tracking, learning and alert workflows rather than building parallel replacements. Prefer one end-to-end implementation sweep with internal checkpoints and concise final results; do not seek permission between ordinary implementation stages already within approval. Interrupt only for genuine blockers, material scope/risk/cost changes, credentials, or required activation authority. Focus on operational MVP rather than repeated reports and incremental approval ceremonies; concise user updates. Existing alerts are reuse targets, not rebuild requirements. Temporary isolated pilots/public exports are not the canonical ingestion architecture. Inspect existing paths before writing replacements and require a demonstrated gap for new components. This preference does not itself authorize new recurring jobs, trades, destructive migrations or weakened security.

Amar values Codex token efficiency and completed bounded stages over repeated partial report handoffs. Notify proactively on completion or blockers. Finish corrections inside the approved stage without repeatedly requesting the same permission; obtain approval before the next stage. Stop/reversal instructions override prior authorization.

## Design traceability

Amar uses medical-device-style design traceability and requested a populated DTM for the trading system: high-level user need → product requirement → specification/design output and associated module/script/mechanism → automated verification protocol with exact test module/script → passing report. Stable IDs and explicit acceptance criteria support forward/reverse trace and change impact. Preserve verification versus real-use validation versus deployment status separately. Historical report PASS applies only to its documented scope/baseline, not automatically to current code. Missing tests/reports stay UNMAPPED or NOT VERIFIED, never inferred from a broad suite. Proposed designs/criteria remain draft until approved. Label legacy, Astra-new and Astra-modified components using evidence; avoid blanket renaming or parallel-stack duplication merely for authorship. DTM structure checks are not product verification; no claim of medical-device regulatory compliance is implied.

## Source ownership

Define an acceptance matrix. Identify the actual dirty checkout and relevant source hashes, not just HEAD. One writer at a time; IDE agent remains read-only. Back up relevant source only, preserve unrelated edits and immutable independent reports. Check competing edits at handoff. Same-checkout work needs a manifest/handoff, not blind copying from older staging.

## Efficient execution

Choose one cohesive stage rather than a monolithic cross-system assignment. Load relevant report sections, files and tests, not all historical logs. Use compact output with full logs on disk, existing guards and fixtures, focused tests during RED-GREEN slices and broader affected regressions at closure. Do not repeatedly build/review unrelated components. Fresh contexts can reduce accumulated bloat but may lose cache benefits; don't promise token savings quantitatively without usage evidence.

Launch durable work with completion notification and retain task/log/process/acceptance handles. On termination inspect real artifacts. Exit0 means normal termination, not task success. Distinguish RUNNING, PARTIAL/STOPPED, BLOCKED, IMPLEMENTED/REVIEW PENDING and ACCEPTED. Continue exact residual acceptance criteria within approved scope unless a real blocker requires user action; avoid unbounded costly retries. Never let a partial checkpoint silently become final completion.

## Termination diagnosis

Inspect logs for actual time/turn/provider limits versus voluntary finalization. Compression or accumulated context estimates are not billed-token totals or evidence of quota exhaustion. Report only supported causes. Oversized scope and voluntary early wrap-up are orchestration failures, not provider-limit proof.

## Safe tests and acceptance

Inspect tests before execution. Use isolated HOME/profile/SQLite, scrub credentials, deny app networking/private-file access and unsafe writes. Application attempts swallowed by exception handling must still fail the guarded run; separately disclose harmless dependency capability probes. Mock external boundaries, never business transitions. Exercise normal constructors and public callers, not extracted AST or source-string assertions.

Use vertical RED-GREEN tests and preserve valid workflows. Independent bug probes sometimes assert reproduction: their exit0 is not acceptance. Convert them into positive invariant regressions rather than calling changed bug observations regressions. Never suppress diagnostics or disable useful behavior to pass negatives.

Promote accepted temporary probes before closeout: copy genuine preserved prior-code fixtures byte-for-byte into tests/fixtures, verify original and independent-copy SHA256, record provenance, and load them only from isolated test helpers (never production). Make guarded selections repository-relative. Generate mounted replay inputs from fresh guarded API outputs rather than depending on preserved temp directories or a developer home. Reuse the deduplicated focused corpus and report remaining platform/dependency requirements; a temporary green run alone is not durable regression coverage.

Independent review verifies current hashes, guarded reruns and adversarial alternate callers. Keep its report immutable; implementer responses are separate. Repair scoped gaps then re-review narrowly. Notify readiness only after acceptance; live qualification and deployment remain separate.
