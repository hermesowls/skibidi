# Integration-ready MVP delivery preferences

Amar explicitly accepts finishing software while he resolves external source access: “Finish the mvp and we’ll plug later.” Disconnected Discord/Skylit should not block independent implementation, source-interface tests, or deployment of accepted software. Do not fabricate REAL observations or claim live qualification. Separate implementation, independent acceptance, deployment, integration readiness, and activation; recurring jobs retain their approval requirements.

“Keep pushing till MVP completion” means continue approved work across worker handoffs, not silently pause after a report. If no worker is running, disclose that honestly. Continue independent work while Amar resolves access. Reuse existing modules instead of parallel replacement workflows; save durable checkpoints and give concise updates.

Escalate genuine blockers with exact minimal actions. Batch known related external checks into one handoff (e.g. app and node TypeScript), avoiding repeated user round trips. Do not bypass safety hooks. User terminal output/screenshots are externally supplied evidence, not an assistant rerun or build/deployment proof.

Completion percentages are clearly labeled engineering estimates tied to the agreed integration-ready versus operational scope, not formal acceptance scores or test counts. Software completion requires the final build/deployment/combined checks; deferred live source validation and scheduling remain explicit.
